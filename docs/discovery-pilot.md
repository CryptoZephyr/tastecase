# Discovery pilot: does Qloo find better test questions?

TasteCase already runs real Qloo-guided discovery. This pilot asks a narrower question: **when the same assistant receives the same fictional dinner briefs, which method finds restaurant pairs a reviewer would actually keep as tests?** It does not measure diners' tastes or prove one approach is generally better.

## Fixed before any live calls

- The eligible catalog is seven previously confirmed public New York places: Eataly - Flatiron, Red Rooster Harlem, Katz's Delicatessen, Le Bernardin, Gramercy Tavern, Via Carota and Union Square Cafe. The task is one fictional dinner for two, with no verified price, diet, availability or accessibility claims. Both approaches use this exact catalog and task.
- Three public-interest pairs are tried in order: Radiohead/Taylor Swift (**calibration**, an already-seen contrast), Radiohead/The Grand Budapest Hotel and Taylor Swift/The Grand Budapest Hotel (**new pairings**). The same three verified Qloo mappings are used for both arms. Their identities and the restaurant list are fixed in the script, not chosen after seeing rankings.
- Qloo-guided selection uses TasteCase's normalised Qloo rankings, software-computed within-query order reversals and existing decision adapter. Generic selection uses the **same free Nemotron model** to choose from all 21 eligible restaurant pairs, but it sees only the public interest labels, catalog names and task—**no Qloo result**.
- Each approach gets one model-selection call per interest pair. One unchanged assistant prompt is called twice per interest profile (six target calls total). **The outputs are shared across approaches** so provider variability cannot favour either selector; this is not a full end-to-end replay of every selected case.
- Initial ceiling: **three Qloo ranking-tool operations and 12 free-model requests** (six selections and six assistant outputs). After the first Qloo failure, one explicit diagnostic tool retry raised the total Qloo ceiling to **four operations**; the free-model ceiling did not change. The script uses zero-price limits, disables model-provider fallback and does not automatically repeat a failed tool operation. The official Qloo client has its own bounded HTTP retries, so tool invocations are **not** exact HTTP-attempt counts. The pre-confirmed catalog/anchors are read from ignored local verification evidence. If a provider fails, the live pilot stops and records a partial result rather than inventing evidence.

## Provider interruption and retrospective fallback

The live pilot stopped on `QLOO_RATE_LIMIT` after **two Qloo ranking-tool operations, zero model requests and zero review cards**. The raw HTTP-attempt total was not retained and is **unknown**. The pinned official client's default is up to three HTTP attempts per query; its envelopes do not expose an exact retry count. The output field `counts.qloo` therefore counts ranking-tool invocations, while `qlooHttpAttempts` is `null` in live mode and exactly `0` in retrospective mode. Qloo's public documentation does not specify a reset time for this key. Do not interpret the error as missing cultural coverage or silently replace the failed live responses.

For an explicitly **retrospective** exercise, `TASTECASE_BENCHMARK_QLOO_SOURCE=historical_recording` reads three previously recorded real MCP rankings from the same seven confirmed places and three anchors. It checks that each recorded query exactly matches the pinned options and signal, re-normalises the recorded provider envelope, hashes each source file and records `source: historical_recording`. It makes **zero new Qloo requests**, but uses live free-model calls for both selection arms and the common assistant. Those older rankings are historical evidence, **not proof that Qloo works now**. The original failed live attempts are reported separately and are not counted as successful retrospective Qloo requests. The raw provider files and the output stay local and ignored; none are committed.

## How to review fairly

Review has two stages. The ignored `.local/discovery-pilot-review-*.json` contains shuffled, source-hidden usefulness cards. Each unique unordered restaurant pair appears once per trial, even if both methods chose it. The initial cards show both fictional profiles, aggregate coverage counts, the pair and the assistant's shared attempts, but omit full ranking orders, reversal lists and method attribution. Record **yes / no / defer**, minutes spent and a reason before opening the separate ignored `discovery-pilot-key-*.json` file. That private file retains both method attributions for a shared card and the full ranking/reversal evidence. Do not give the reviewer the raw result or key file during stage one.

In stage two, keep the initial usefulness decision unchanged, inspect the private evidence and record evidence sufficiency separately. Stage two reveals sources and is not blind. Disclose prior knowledge of the pilot or its results; hiding fields does not guarantee blindness for a reviewer who already knows the selections. Old review packets that exposed reversal lists must be regenerated from the original saved evidence, not from written summaries, before collecting new first-stage decisions.

Mark **yes** in stage one only if the specific question is worth keeping as a repeatable test for an AI concierge and could inform a real review decision. Confirm evidence sufficiency separately in stage two before preserving a test. A rank reversal alone is not enough. Missing Qloo coverage means unavailable evidence, not negative evidence; a partial trace does not prove missing assistant activity. Same recommendations and unchanged runs may be legitimate. A reviewer's yes is not an automatic correctness pass or an approved suite expectation. Attribute a shared card's identical decision to both methods without counting it as two independent discoveries.

After review, compare useful questions **out of attempted cases** for the two new pairings, with calibration shown separately. Also report provider and model call counts, missing/unavailable evidence, repeat consistency, review minutes, rejections, deferrals and whether any human-approved suite tests were actually created. With only two fresh pairings this is an exploratory pilot: report examples and uncertainty, **not a general superiority, user-satisfaction or conversion claim**.

## Running it locally

The script requires `TASTECASE_BENCHMARK_LIVE=1`, `OPENROUTER_API_KEY`, `TASTECASE_QLOO_FIXTURE_DIRECTORY` pointing at existing confirmed mapping evidence and `TASTECASE_BENCHMARK_OUTPUT_DIRECTORY` pointing to the existing ignored repository `.local` directory. From the repo root run `node --import tsx scripts/benchmark-discovery.ts`. The default **live** mode also requires `QLOO_API_KEY`. The retrospective mode requires `TASTECASE_BENCHMARK_QLOO_SOURCE=historical_recording` instead of a Qloo key and expects the three pre-existing `expanded-rank-*.json` recordings in that same evidence directory. Do not commit the private review packet, source key or local evidence. Importing the script or running its unit tests makes **no provider calls**.

Before writing any of the three artifacts, the script serializes and checks all three for known local credentials and credential-shaped authorization strings, including echoed keys in recommendations, errors and JSON property names. Unsafe content stops persistence rather than altering pinned evidence. Provider-error messages use the runner's existing redaction. Artifact writes are private and exclusive, so existing evidence is not overwritten. Tests use synthetic strings, never live credentials.

The only production components reused are the official Qloo adapter, computed contrast facts, decision adapter and configured assistant adapter. This is an **offline comparison**, not a new production endpoint or an automatic reviewer.
